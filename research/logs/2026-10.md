# 2026年10月の研究・実装ログ

## 2026-10-02: simulation操作性能の実測とhot path改善（#610）

- 目的: 双腕cube操作時の入力失効を、接触solver原因と仮定せず実測で切り分ける。
- 実施内容: 同モデルのfree-space/片側/双腕実接触、中立/微小移動を基点blobと比較し、Python検査と観測の固定費が大きいことを確認した。閾値・全substepを維持して検査実装、不変identity生成、共同snapshot共有、中立IKを効率化した。続いてlive qpos改変をfresh commit guardで拒否し、表示sampleを非変更読取りにした。通常Workbenchの入力取得を約60Hz、frame公開をticket/phase/tick変化駆動としてtimer待ちを削減した。
- 検証と実験的価値: 全測定tickのqpos/qvel・接触/力・integration stateは基点と完全一致し、操作能力を維持したhot path改善を実測した。条件・数値・再開scriptの所在は[性能測定note](../../docs/experiment-notes/2026-10-02-simulation-performance.md)へ分離する。
- 診断: 元receiptと0.2秒を維持し、invalid timestamp/pre-trial/future/staleを実age付きで区別する。実時計とbrowserのsoftware fixtureで入力・Task・STOP/ticket隔離を確認した。
- 判断・未解決事項: Mappingのtrigger消費境界を含まないlatest-only/ingest ACKは採用しない。有界遷移FIFOと消費ACKの具体設計を残したがtransport実装は見送り、既存buffer滞留リスクを保持する。大型fixed boxへの双腕接触に加え、実100mm cube反対面のnative checkpointも比較した。独立tick比較をユーザーの連続軌跡・把持成功へ読み替えず、実device性能と200ms超過原因は未確定とする。
- 関連Issue: #610。#609未mergeの基点を維持し、GitHub操作と独立レビューは親へ引き継ぐ。

## 2026-10-02: Workbench入力周期と停止理由の修正（#608）

- 描画rAFに依存した40 ms取得制限を、共通lifecycle内の独立timerへ変更した。描画fps低下による追加の入力間引きを除き、毎回の実sampleと取得時刻を保持する。
- Task/予算/入力失効/STOPの終端後に到着する同ticket入力をtransport境界で棄却し、元の停止理由・保存結果を保つ。未開始・旧ticket・不正入力・権限違反の拒否は維持する。
- 基点コードの模擬60/30/10Hzでは入力間隔50/66.7/100msを再現した。実MuJoCo workerでも各終端後にactive-trialエラーが二次発生することを再現した。修正は入力符号、0.2秒freshness、中立待ち、physics、model、Task条件を変更しない。
- これはsoftware回帰の修正であり、利用者の各停止原因はprofile/terminal記録が未取得のため未確定。実Gamepad機種・実機・参加者による受入や操作性能の研究結果を主張しない。

## 2026-10-02: Workbench受信履歴の消費順修正（#610 / PR #611）

- 目的: fresh入力がlocal queueにあるのに、古いlatched sampleでtickを先行させる停止経路を除く。
- 実施: 有界batchの全sampleをvalidation・Mapping離散状態へ通してから最新入力で1tickを進める。元receipt、trigger解除・中立・切断・session/sequence検査、STOP優先を維持し、古いmotionは再生しない。
- 検証: 合成入力と実MuJoCo、実worker WebSocketで190/250/700msの明示停滞を検査した。条件・結果は[追試note](../../docs/experiment-notes/2026-10-02-simulation-performance.md)に分離する。
- 研究上の意味: 描画/physicsの処理遅延を入力喪失と誤認する経路を減らす。平均低遅延化の既存値を、本修正の受入根拠として使わない。
- 未解決: 本当の0.2秒超の無入力はstrictに無効となる。試行を保持したsimulation一時停止と明示resume、wall budget・formal validityのpolicy選択は未実装。ユーザー発生環境・terminal記録は未取得で、通常運用の完全解消や実device/participant受入を主張しない。

### #610 input batchingのreview修正

初回armingには中立自身のfresh receiptを要求し、連続64件batchでもwall/input-wait監督を維持した。終端後batchの不正入力も全件検査する。receipt gapは診断に限定し、新規formal-validity ruleを追加しない。同一worker wire/clockの203ms stale red→greenと61秒の合成60Hz・実WebSocket/実MuJoCo継続を確認した。ユーザー元run・実Gamepadは未再現で、source gap時の一時停止・明示再開policyは別判断のまま維持する。条件と結果は上記追試noteを参照する。

### #610 再open後のfault前再確認

main CIの61秒試験は53.1秒simulation時に210ms staleで失敗した。以前のgreenは全境界の保証ではない。
drain後、source read後、clock評価時に210ms停止しfresh入力をqueueへ入れる3条件を決定的に再現した。

これはsoftware回帰と研究利用上の再現性改善であり、実device受入やpause/resume policy変更ではない。

## 2026-10-03: Workbench低遅延置換候補

- 目的: 物理条件・入力意味・Task・必須記録を維持し、取得、表示、通信、終端保存の待ちをExecution周期から分離する。
- 実施: 60Hz取得からReact root updateを外し、10Hz計器/展開時4Hz詳細へ分けた。固定buildを既定にし、source/lock/asset byteを照合する。単一Execution owner、STOP専用slot、入力/制御FIFO、最新表示slotとsender、非同期終端記録を実装した。
- 条件/検証: dynamic-cube-push、control 1/60 s、physics 1/600 s、age 0.2 s、Task 60 sを維持。専用Edge/service/native workerで通常60秒と20 retryを測定し、最終候補の約10秒RTFは0.99782–1.00085、render p95は49.6/49.7 msだった。詳細とraw evidence境界は[実測note](../../docs/experiment-notes/2026-10-03-workbench-low-latency.md)を参照する。
- 研究上の意味: 表示consumerの停滞と本当の入力停止を分離して検査でき、記録成立後の入力待ち期限を明示できる。表示/physics/Taskの正本は増やしていない。
- まだ言えないこと: baselineも同系列では等速だったため、元障害の恒久解消や候補の性能優位は未証明。合成系列は接触未到達で、実Gamepad/参加者/接触操作受入ではない。GIL競合とshared-memory表示processへの完全分離は未解消である。
